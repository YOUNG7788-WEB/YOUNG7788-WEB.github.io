我从零折腾两台 VPS：买机器容易，养机器才是正片

2026-11-14 · 约 13 分钟

最开始我对 VPS 的理解很朴素：买一台云服务器，装上系统，服务跑起来，手机能连，就算完成。真的折腾一圈才发现，“能连”是第一关，线路、维护、备份和账单，每一关都能让我重新打开 PowerShell。

最开始我对 VPS 的理解很朴素：买一台云服务器，装上系统，服务跑起来，手机能连，就算完成。真的折腾一圈才发现，“能连”是第一关，线路、维护、备份和账单，每一关都能让我重新打开 PowerShell。

第一步：买的到底是什么。

我在 Evoxt 买的是平台提供的虚拟机，不是先买一台物理服务器再自己装虚拟机。翻了一下订单，时间线是：2026 年 9 月 27 日先订购美国加州 VM-1，后来在 10 月 14 日订购马来西亚优质线路 VM-0.75。两笔都是按月付费，也都选了自动每周备份。官网下单时，流程是选地区和套餐、核对计费周期及可选项、完成支付，然后等订单确认、付款确认和“机器已部署”邮件。订单邮件到了不等于机器已经能用，我会等部署通知，再去控制台看状态。具体价格会随时间变化，文章不拿旧账单当报价表。

第二步：拿到虚拟机，先别急着往里塞东西。

控制台给出系统、地址和初始登录信息。我先确认虚拟机是 Running，再看系统版本、能否连接、磁盘和内存是否正常。美国那台最初收到的是 Ubuntu 24.04，后来有过重装和方案调整；马来西亚的部署通知显示 Ubuntu 26.04。重装会清掉系统盘上的旧配置，所以每次动手前得弄清什么要备份，什么可以丢。

第三步：在 Windows 用 PowerShell 连上去。

我不是在电脑里装了个“Linux 虚拟机”，而是从 Windows 终端远程登录云上的虚拟机。最基础的入口是 ssh 用户名@服务器地址。第一次连接要核对主机指纹；看到密码或密钥口令提示时，输入内容不会显示在屏幕上，这是正常的。连接成功后，我会先看系统信息、服务状态和网络，而不是一上来执行一大段来路不明的脚本。需要把文件从服务器取回本机，用的是 scp；需要核对下载文件是否一致，可以在 PowerShell 里用 Get-FileHash。下面把关键命令和排错顺序都列出来；真实地址和密钥当然不放在公开网页上。

第四步：部署服务。

早期试过不同方案，后来两台机器都围绕 sing-box 做过配置。实际操作并不是“复制教程，回车，完事”：要核对安装来源、检查配置格式、确认服务启动、设开机自启，再从手机端导入独立的连接信息进行测试。服务端显示 active，只能证明进程在跑；手机能不能连、实际应用顺不顺，必须另测。安装和服务管理的命令我对照了 sing-box 官方文档；具体协议字段随版本变化，实际配置时仍要以官方说明为准。

第五步：手机实测，别只盯一个延迟数字。

我测过马来西亚和美国节点，手机上看到的延迟大致是前者 100 多毫秒、后者 200 多毫秒。这个数字能说明当时的响应情况，不能直接等于下载速度，更不能代表晚高峰长期表现。后来我也比较过其他线路，发现服务器配置高不一定更快，跨境路由的影响很大。我的结论很朴素：先用真实场景测，再决定要不要继续花钱折腾。

第六步：维护。

服务能用以后还要看开机启动、系统更新、失败登录拦截、密钥登录、备份和到期提醒。这里尤其要老实：回头翻操作记录，有些安全加固当时确实还没做完，不能因为“手机连上了”就写成“服务器已经万无一失”。账单也是，收到续费提醒并不等于已付款。我会定期核对控制台、服务状态和实际连接；遇到超时先分清是机器停了、服务没起来，还是线路本身慢。PowerShell 只是操作台，真正有效的是每一步都有检查结果和回退办法。

我把过程整理成脱敏流程和操作小抄：ssh 负责连接，scp 负责传文件，Get-FileHash 核对文件；Linux 端的服务状态与日志命令负责确认服务是否正常。真实 IP、密码、二维码、连接参数、订单号和账单不会公开。这样别人能看懂我怎么走过来，也不会顺手拿到我家的钥匙。

把部署这一步展开：从安装到手机填写。

前面是我当时折腾两台机器的时间线。下面这份是按官方文档整理的通用复现示例，方便以后重装时对照；它没有在一台新机器上重新跑过，不能冒充另一份实测报告。真实配置里的 UUID、密钥和地址都换成了占位符。服务器按月付费，是我原来的个人开销；这个网站本身仍用免费的 GitHub Pages。

1．先分清两个终端。

PowerShell 在 Windows 上；SSH 登录成功以后，提示符变了，后面的 Linux 命令才是在云服务器里运行。我以前最容易把这里混在一起。先在 PowerShell 里检查连接端口，再登录：

$serverAddress = "替换为自己的服务器地址"
$sshPort = 22 # 如果自己改过 SSH 端口，这里也要改
Test-NetConnection -ComputerName $serverAddress -Port $sshPort
ssh -p $sshPort "root@$serverAddress"

TcpTestSucceeded 是 True 说明 TCP 端口能连，不等于 SSH 密码已经正确，更不等于后面的代理服务能用。第一次出现主机指纹，和控制台等可信渠道核对后再接受。服务器重装后指纹可能变化，也要核对，别看见提示就闭眼删记录。

2．在 Ubuntu 安装官方软件包。

先查看系统版本、更新软件索引，再装基础工具。这里的命令在 SSH 会话中运行，不是在本机 PowerShell 里运行：

cat /etc/os-release
sudo apt-get update
sudo apt-get install ca-certificates curl openssl nano
sudo install -d -m 0755 /etc/apt/keyrings
sudo curl --fail --silent --show-error --location https://sing-box.app/gpg.key --output /etc/apt/keyrings/sagernet.asc
sudo chmod 0644 /etc/apt/keyrings/sagernet.asc

把下面的软件源内容写入文件。每一段执行后先看有没有报错，别让上一条失败了、下一条还在热闹地跑：

sudo tee /etc/apt/sources.list.d/sagernet.sources > /dev/null <<'EOF'
Types: deb
URIs: https://deb.sagernet.org/
Suites: *
Components: *
Enabled: yes
Signed-By: /etc/apt/keyrings/sagernet.asc
EOF
sudo apt-get update
sudo apt-get install sing-box
sing-box version

安装来源与后续变更见 官方包管理器安装说明 ↗。最后一条应显示实际版本；如果软件源、签名或网络报错，先处理报错，不改用不知道谁维护的一键包凑数。

3．生成每台机器自己的凭证。

下面三条分别生成 UUID、REALITY 密钥对和一个短标识。输出只放在自己的安全记录里：

cat /proc/sys/kernel/random/uuid
sing-box generate reality-keypair
openssl rand -hex 4

密钥对里有私钥和公钥：私钥留服务器，手机用公钥。别看它们长得差不多就随便复制，填反了可不会因为我态度诚恳就连上。两台服务器各自生成一套，手机里也分别命名，省得以后排错时连自己到底在测哪台都不知道。

4．写配置，再检查配置。

我后来的方案围绕 VLESS／REALITY。下面给出一个字段对照示例：把 YOUR_UUID、YOUR_PRIVATE_KEY、YOUR_SHORT_ID 和两处 YOUR_HANDSHAKE_HOST 替换成自己的值，保留引号。握手目标需要从服务器可达并符合 REALITY 的要求，不能随手填个域名当装饰。字段解释见 VLESS 入站 ↗ 与 REALITY TLS 配置 ↗。

{
  "log": { "level": "warn", "timestamp": true },
  "inbounds": [{
    "type": "vless",
    "tag": "vless-in",
    "listen": "0.0.0.0",
    "listen_port": 443,
    "users": [{ "uuid": "YOUR_UUID", "flow": "xtls-rprx-vision" }],
    "tls": {
      "enabled": true,
      "server_name": "YOUR_HANDSHAKE_HOST",
      "reality": {
        "enabled": true,
        "handshake": { "server": "YOUR_HANDSHAKE_HOST", "server_port": 443 },
        "private_key": "YOUR_PRIVATE_KEY",
        "short_id": ["YOUR_SHORT_ID"]
      }
    }
  }],
  "outbounds": [{ "type": "direct", "tag": "direct" }],
  "route": { "final": "direct" }
}

用 sudo nano /etc/sing-box/config.json 打开配置文件，填好后保存。已有配置先备份，再编辑。然后检查：

sudo sing-box check -c /etc/sing-box/config.json
sudo systemctl cat sing-box
sudo ss -lntp

第一条检查语法和字段；第二条确认服务实际从哪里读配置；第三条看 443 有没有被别的程序占用。配置检查通过，也只是检查通过，还没到手机能用的那一步。如果服务读取的路径与示例不同，先统一路径。不要为了空出端口就把一个不认识的服务停掉。

5．放行端口，启动服务。

服务商控制台的入站规则要允许自己使用的服务端口。若系统本身启用了防火墙，还要检查系统规则；SSH 用哪个端口，就先确保哪个端口仍然放行，保留当前连接并用第二个窗口验证。示例的服务端口是 TCP 443，不需要把所有端口统统打开。

sudo systemctl enable --now sing-box
sudo systemctl is-active sing-box
sudo systemctl is-enabled sing-box
sudo journalctl -u sing-box --output cat -e

这里分别看启动是否成功、是否正在运行、是否开机启动，以及具体日志。若是已经运行的服务，改配置后先通过检查，再执行 sudo systemctl restart sing-box。active 不是结束语，客户端连接仍然要单独验收。

6．手机端各字段怎么对。

在支持这个协议组合的客户端里新建配置，逐项对应；不同客户端叫法可能略有不同：

  • 地址填服务器公网地址，端口填服务端的 listen_port。
  • 协议选 VLESS，UUID 填刚生成的 UUID，flow 对应 xtls-rprx-vision。
  • 开启 TLS，SNI／服务器名称填同一握手目标。
  • REALITY 公钥填刚生成的公钥，short ID 填同一个短标识；私钥不进手机配置。
  • 若客户端要求指纹，按其兼容说明填写；不要把“跳过证书校验”当成通用修复开关。

保存后先尝试连接，再打开实际网页或应用。连接日志报认证错误，就回头对 UUID、公钥、short ID 和 SNI；超时则先查地址、端口、入站规则和线路。我的手机当时测到马来西亚 100 多毫秒、美国 200 多毫秒，那是那一刻的延迟，不是套餐自带的永久承诺。

7．维护不是再装一次。

配置改动前留一份私密备份，记住当前版本；升级后重新检查配置并测试连接。异常时先看日志和端口，别把“重装系统”当万能橡皮擦。账单是否续上、控制台备份是否成功、备份能不能恢复，也都得真的点进去看。安全加固里还有没做完的项目，我会接着做，不能靠文章替机器毕业。
