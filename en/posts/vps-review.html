VPS setup and maintenance

2026-11-14 · 7 min read

A retrospective on deployment, phone tests and maintenance.

At first my idea of a VPS was simple: buy a cloud server, install an operating system, start a service and connect from my phone. I found out that a working connection was just the first hurdle. Routing, maintenance, backups and bills all gave me reasons to open PowerShell again.

What did I actually buy?

I rented virtual machines from Evoxt rather than buying hardware and setting up my own hypervisor. I ordered a California VM-1 on September 27, 2026 and a Malaysia premium-route VM-0.75 on October 14. Both were billed monthly, with automatic weekly backups selected. On the website I chose a region and plan, checked the billing cycle and extras, paid, and waited for order, payment and deployment emails. An order email doesn't say that a machine is ready. I wait for deployment and check the console. Prices change, so my old bills aren't a price list.

The first checks on a new VM.

The console provides the OS, address and initial login information. I check that the VM is running, then check the OS version, connectivity, disk and memory. The US machine initially had Ubuntu 24.04 and later went through reinstalls and configuration changes. The Malaysia notice showed Ubuntu 26.04. Reinstalling wipes configurations on the system disk, so I work out what needs a backup before starting.

Connecting with PowerShell on Windows.

I used a Windows terminal to log in remotely, not a VM installed on my PC. The basic command is ssh username@server-address. Check the host fingerprint on your first connection. Passwords and key passphrases don't appear as you type them. Once in, I check the system, services and network before running any script. I use scp to copy files back and Get-FileHash in PowerShell to check them. The commands below use placeholders instead of my address and keys.

Deploying the service.

After trying different approaches, I configured sing-box on both machines. I checked the source of the package and the configuration format, verified the service started, set it to start at boot, then tested separate connection details on my phone. An active server process only tells me it's running. Actual mobile connectivity and application behavior need their own checks. I used the official documentation for setup and service commands. Protocol fields can change between versions.

Testing on the phone.

I saw latency in the low hundreds of milliseconds for Malaysia and above 200 ms for the US. That was responsiveness at the time of the test, not a measure of download speed or long-run peak-hour performance. Comparing other routes taught me that higher server specs don't guarantee a better connection. Cross-border routes matter a great deal. I test my actual use case before spending more.

Maintenance.

Once the service worked, I still had to look at boot startup, updates, repeated login failures, key-based login, backups and renewal reminders. Some hardening work was still open in my records. A connection on my phone doesn't say anything about whether it's done. A renewal notice doesn't mean the bill was paid. I check the console, service status and real connections regularly. On a timeout I first work out whether the VM is down, the service stopped, or the route is slow. PowerShell is my console. The useful part is having a result and a way back at each step.

I kept a redacted workflow and cheat sheet. SSH connects, SCP moves files, and Get-FileHash checks them. On Linux, service and log commands help me verify operation. My real IP addresses, passwords, QR codes, connection parameters, order numbers and bills stay private.

From installation to entering the phone settings.

The timeline above is about my two machines. The example below comes from the official docs and is for reference on a future reinstall. I haven't rerun it on a fresh machine. UUIDs, keys and addresses here are placeholders. The servers are a personal monthly expense. The site itself is hosted on free GitHub Pages.

1. Know which terminal you're in.

PowerShell runs on Windows. After SSH login, the prompt changes and subsequent Linux commands run on the server. I used to mix that up. First check the port in PowerShell, then log in.

$serverAddress = "YOUR_SERVER_ADDRESS"
$sshPort = 22 # Change this if SSH uses a different port
Test-NetConnection -ComputerName $serverAddress -Port $sshPort
ssh -p $sshPort "root@$serverAddress"

When TcpTestSucceeded is True, the TCP port is reachable. It doesn't validate the SSH password or say the service will work. Compare the first host fingerprint with the provider console or another trusted source. Reinstalling can change it. Verify that change before removing the remembered fingerprint.

2. Install the official package on Ubuntu.

Check the OS, update the package index and install the tools. Run these in the SSH session.

cat /etc/os-release
sudo apt-get update
sudo apt-get install ca-certificates curl openssl nano
sudo install -d -m 0755 /etc/apt/keyrings
sudo curl --fail --silent --show-error --location https://sing-box.app/gpg.key --output /etc/apt/keyrings/sagernet.asc
sudo chmod 0644 /etc/apt/keyrings/sagernet.asc

Write the package source as shown below. Check each block for errors before moving on.

sudo tee /etc/apt/sources.list.d/sagernet.sources > /dev/null <<'EOF'
Types: deb
URIs: https://deb.sagernet.org/
Suites: *
Components: *
Enabled: yes
Signed-By: /etc/apt/keyrings/sagernet.asc
EOF
sudo apt-get update
sudo apt-get install sing-box
sing-box version

See the official package-manager instructions ↗ for sources and changes. The last command should show the installed version. If the repository, signature or network fails, investigate the error before using another distribution method.

3. Generate separate credentials per machine.

These commands generate a UUID, a REALITY key pair and a short ID. Store the output securely.

cat /proc/sys/kernel/random/uuid
sing-box generate reality-keypair
openssl rand -hex 4

Keep the private key on the server and enter the public key on the phone. Use a separate set for each machine and give the phone profiles distinct names so you know which one you're testing.

4. Write and check the configuration.

My later setup used VLESS with REALITY. Replace YOUR_UUID, YOUR_PRIVATE_KEY, YOUR_SHORT_ID and both copies of YOUR_HANDSHAKE_HOST with your own values, keeping the quotes. The handshake target must be reachable from the server and meet REALITY's requirements. See VLESS inbound ↗ and REALITY TLS settings ↗.

{
  "log": { "level": "warn", "timestamp": true },
  "inbounds": [{
    "type": "vless",
    "tag": "vless-in",
    "listen": "0.0.0.0",
    "listen_port": 443,
    "users": [{ "uuid": "YOUR_UUID", "flow": "xtls-rprx-vision" }],
    "tls": {
      "enabled": true,
      "server_name": "YOUR_HANDSHAKE_HOST",
      "reality": {
        "enabled": true,
        "handshake": { "server": "YOUR_HANDSHAKE_HOST", "server_port": 443 },
        "private_key": "YOUR_PRIVATE_KEY",
        "short_id": ["YOUR_SHORT_ID"]
      }
    }
  }],
  "outbounds": [{ "type": "direct", "tag": "direct" }],
  "route": { "final": "direct" }
}

I use sudo nano /etc/sing-box/config.json to edit the configuration after backing up the existing file. Then I check it.

sudo sing-box check -c /etc/sing-box/config.json
sudo systemctl cat sing-box
sudo ss -lntp

The first command checks syntax and fields. The second shows where the service reads its configuration. The third checks whether anything is already listening on port 443. If the service reads a different path, resolve that before proceeding. Identify a service before stopping it to free a port.

5. Allow the port and start the service.

The provider's inbound rules must allow the service port. Check the OS firewall if it's enabled. Keep the SSH port allowed, leave the current session open and verify a second connection. This example needs TCP 443 for the service.

sudo systemctl enable --now sing-box
sudo systemctl is-active sing-box
sudo systemctl is-enabled sing-box
sudo journalctl -u sing-box --output cat -e

These commands start the service and check if it's running, enabled at boot, and what the logs say. If it's already running, validate the updated configuration before running sudo systemctl restart sing-box. Verify the client separately.

6. Match the phone fields.

In a client that supports this combination, create a profile. Field names can vary.

  • Use the public server address and the server's listen_port.
  • Select VLESS and enter the UUID you generated. Set the flow to xtls-rprx-vision.
  • Enable TLS and use the same handshake host as the SNI or server name.
  • Enter the REALITY public key and the matching short ID. Keep the private key on the server.
  • If the client needs a fingerprint, follow its compatibility instructions. Skipping certificate verification isn't a general fix.

Save it, try connecting, then open a real page or app. For errors in the authentication log, verify the UUID, public key, short ID and SNI. For a timeout, check the address, port, inbound rules and route. The phone readings of over 100 ms for Malaysia and over 200 ms for the US were snapshots, rather than permanent attributes of the plans.

7. Maintenance goes beyond reinstalling.

Make a private backup and record the current version before changing the configuration. Check it and test the connection again after an upgrade. Start with logs and listening ports when something goes wrong. Check whether renewals went through, console backups ran successfully and the backups actually restore. I still have hardening work to do.
